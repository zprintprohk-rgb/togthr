At 00:50, `d79c49c` ran a prod smoke test that reported 7/21 blog accessibility 10/10 PASS. At 01:00 (10 minutes later), this 7/22 verify cron found 7/21 8 locales back to **timeout 30s** (not even 404 anymore — TCP connection reset before the worker responds).

**Root cause hypothesis (consistent with all evidence, still unproven from cron side — see §3 for the user-side evidence needed)**:

`.open-next/server-functions/default/handler.mjs` (a 4.5 MB+ minified bundle produced by `npm run cf-build`) contains 47 `async function M(...)` per-page handler declarations. The JS scoping rule is "last declaration wins" for same-scope `async function M` — so the wrangler bundler must generate a wrapper that maps each URL to a specific `M` by some lookup table. For 7/15/7/16/7/18/7/20/7/14, the wrapper has the right entries and routes to the right `M`. **For 7/21, the wrapper entry is missing** — so the request goes to a default 404 handler (yesterday 18:00) or hits a worker instance with a broken dispatch that resets the connection (today 01:00). Pushing any new per-locale page.tsx (e.g. 7/22) is **likely** to either re-introduce the same bug (if wrangler's wrapper build is non-deterministic for routes added in batches) or be the 2nd route with a missing dispatch entry.

### 1.2 The d79c49c "7/7 PASS" was a false positive

`d79c49c test(smoke): prod smoke script + 7/7 PASS report (2026-07-21)` added `scripts/smoke-prod.py` and reported:

```
| 1 | Blog accessibility (latest 10 /en/blog/{slug}) | PASS (10/10) |
```

10/10 PASS means: at 7/22 00:50:46 UTC, the smoke script fetched 10 different `/en/blog/{slug}` URLs (including the 7/21 one) and got 200 OK for all 10. But 10 minutes later (7/22 01:00), the same 7/21 URL timed out after 30s.

**The most plausible explanation**: at 00:50, CF edge cache had cached a successful 7/21 response from an earlier moment (e.g. an earlier 7/21 deploy run #195 succeeded enough that the edge cached the 200 for a few minutes), and the smoke test hit that cache. By 01:00, the cache entry had expired and the underlying worker dispatch bug re-exposed itself.

**Implication for 7/22 work**: I cannot trust the 7/22 00:50 smoke as evidence that 7/21 is fixed. I must verify with a fresh, cache-busted request (which I did, with `-UseBasicParsing -TimeoutSec 30`). Fresh requests time out → 7/21 is still broken. The smoke script would benefit from adding `?cb=<timestamp>` to every URL or using `Cache-Control: no-cache` headers — but that's a follow-up task, not a 7/22 blocker.

### 1.3 Why producing 7/22 content now is a net negative

If I had produced 7/22 content today (8 locale page.tsx + 1 blog-posts entry + 8 cover images + 1 commit + 1 push):

- **Net positive if 7/21 dispatch was fixed**: +8 live URLs, +1 build quota, ~3 KB of unique body content per locale, normal daily content.
- **Net negative if 7/21 dispatch is still broken** (current reality): +8 new 404/timeout URLs (one per locale), +1 build quota wasted, +1 GH Actions run, +new thin-content / doorway pages that Google might index as 7/22 (worse for SEO than not having Navigable URLs at all).

I cannot tell with 100% certainty that 7/22 page.tsx would 404 (it's possible that wrangler's bundle dispatch for 7/22 works while 7/21 doesn't — they are different routes). But:

- The bug is in the wrangler URL→M dispatch table. Both 7/21 and 7/22 would be new entries. If wrangler mis-handles one new entry, it likely mis-handles the other.
- The 18:00 verify report and the 7/22 00:50 → 01:00 zigzag both point to a *non-deterministic* wrangler build behavior for new per-locale routes.
- Even if 7/22 ships and 7/21 still 404s, that creates an inconsistent blog archive (some posts live, some not, no obvious reason to a reader) — worse for the site than a 1-day skip with a documented reason.

So the conservative call is: **skip 7/22 content, write this verify report, push it, escalate user**. The user can either fix 7/21 dispatch and unblock 7/22 in the same work session, or explicitly tell me to ship 7/22 anyway and accept the risk.
